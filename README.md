## 💠 Общие требования
В вашем распоряжении более 2-х недель, проект можно сдать в любой из дней вплоть до дня сдачи экзамена (26.07.2026).
Без репозитория с проектом сдача не назначается, все файлы проекта должны располагаться в репозитории на Git Hub и иметь коммиты в колличестве равным вашим 
изменениям внесенным в проект. Репозиторий должен иметь понятную структуру (если проект большой проясните навигацию в README.md или где либо еще в репозитории).
Репозиторий должен иметь все файлы которые необходимы для запуска проекта (исключение папка node_modules и файлы конкретных IDE).
В README.md обязательно должны быть указаны ссылки на этот файл (конкретное техническое задание), ссылка на владельца (если вы форкнули или использовали 
исходные данные другого человека), ссылки на нейросети и инструменты или перечисление их (если вы их использовали в работе над проетом).

> ⚠️ **Важно:** Если ваша документация есть в файлах кроме README.md и вы расчитываете на ее вес - укажите ссылки на эти файлы или их названия.

### Шаг 1: Фундамент проекта Node.js + Three.js + WebSocket (Socket.io)

**Цель:** Создать работающий сервер с комнатами и базовым WebSocket соединением.

#### Инициализация
Ваша задача создать проект - root package и вложенные директории.
Старайтесь сделать все максимально удобно и при этом по стандартам 
модульной разработки. Избегайте больших и неудобных файлов которые создаете вручную, 
разделяйте логику не только между скриптами, но и между модулями.
Для начала инициализируйте `node` и заполните важные части `package.json`.
Добавляйте зависимости только по надобности, реализуйте несколько веток или разные папки для версионности
вашего приложения - это упростит и ускорит разработку. Перед испытанием или внедрением новой функции или 
механики постарайтесь убедиться, что прежняя версия останется нетронутой для возможного возврата к ней в
случае проблем. Ведите историю коммитов на Git Hub с комментариями к ним, так будет легче найти кодовый участок для восстановления
или для того что бы потом восстановить весь прогресс создания вашего приложения в документации.
Постарайтесь сти проект с чистой архитектурой, временные файлы держите в папке `temp`, скрипты в `src` папке, тестовые в `test`, статичные 
файлы в папке `public` и так далее.
Не забывайте что проект созданный в ходе обучения может упросить вам путь создания или являться структурным планом для реализации.
В процессе разработки вы можете кидать ссылки к этому репозиторию для того, что бы я смог вам помочь с чем либо разобраться в вашем проекте, если есть 
такая необходимость, так же можно написать issues в этом репозитории или добавить меня как контрибутора в свой проект. Однако советы которые я буду 
давать будут носить рекомендательный характер и не будут решать задачу на прямую.
Не забывайте, что очень важно называть файлы понятно и указывать им нужные типы расширений. Обращайте внимание на то содержит ли файл класс или 
просто является структурным скриптом.
Не делайте больших вложенностей, старайтесь избегать глубины вложенности скриптов из за проблем с сылками и зависимостями - лючший вариант держать все
кодовые файлы на одном или нескольких уровнях вложенности.

### Шаг 2: База данных и система аккаунтов может быть любой

Более важно то, что вы заявляете - если данные хранятся там же где и расположен сервер, 
вы должны указать это в документации, если используете кеширование как основную базу - 
этого недостаточно (исключение удаленный сервер Redis). То какое количество или какие именно
данные вы храните не имеет значения, вы в праве сами выбирать что и на какой основе хранить
- важна декларация и конкретный факт того что это работает! Так же если вы реализовали
только лишь сохранения на клиенте (кеш, coocki) и не реализовали полностью серверное
хранение данных, шанс на то что вы все равно получите бал за это задание есть - вам стоит просто
реализовать, что то сверх требуемых пунктов и предоставить данные об этом!

### Шаг 3: 3D клиент на Three.js (базовый)

Каждая сессия которая начинается с передачи клиентских данных с сервера в браузер пользователя
использует ограниченное количество ресурсов самого клиента - надо помнить об этом. Не старайтесь сделать полный функционал, 
но старайтесь реализовать работоспособный прототип. Браузер пользователя имеет ограниченные ресурсы (нужно балансировать с нагрузкой), 
машина пользователя так же может столкнуться с ограничениями, в конце концов - если вы протестируете все, что вы сделали на смартфоне, вы
поймете как стоит отнестись к нагрузке на клиент - ведь смартфон яркий пример отсутствия больших ресурсов. Выход - пользоваться CDN ссылками 
для картинок, текстур, моделей и аудио, но помните что для подгрузки удаленно клиенту потребуется время - выделите ему его, сделайте экран загрузки, 
что бы защитить игру от ошибок и неожиданных триггеров и подгрузите то что необходимо тогда когда это необходимо. 
Выбор - делать сессии или комнаты для пользователь - это так же конкретно ваше решение, если логика приложения строго диктует это - лучше сделать, 
но пока можете реализовать заглушками до самого последнего этапа, что бы не терять много времени на дополнительный функционал.
Важно! Клиент должен видеть другого клиента если тот находится онлайн с ним в сессии, а для этого все объекты и события должны соответствовать как и технические аспекты!

### Шаг 4: Сетевая синхронизация

Сервер не обязательно делать сразу, вы можете пользоваться `npx` или `vite` для запуска в режиме разработки, 
но надо помнить, что в итоге нужно реализовывать именно свой сервер используя любые модули - `http`, `express`, `fastify` и тд.
Сервер должен полностью отображать логику обмена данными, работа с запросами по желанию, но вот сокетное соединение должно быть.
И соединение через сокеты должно обрабатывать все те случаи которые вы задаете на клиенте. Сервер видит и общается со всеми пользователями 
онлайн на нем, по этому используйте как личное обращение к выбранному клиенту, так и всеобщую рассылку. Какие то редкие 
операции можно сделать и с помощью CRUD операций, но постарайтесь не перенасыщать сервер дорогими обменами данных c API, сейчас наша цель - мультиплейер.

### Шаг 6: Деплой, документация, сдача

Деплой - важный шаг, если вы сделали все и на отлично, но не разместили приложение (сервер) на хосте, 
что бы получить возможность удаленно взаимодействовать с ним в любое время с любого устройства, значит вы сделали не все - 
и высшую оценку вы получить не сможете ( исключение - все домашние задания были сданы на 5). По этому, как только вы 
убедились, что все работает на вашей локальной машине - ищите пути деплоя на хосте, Git Hub хоть и не на прямую, но косвенно с этим помогает.

#### 6.1 Подготовка к деплою
- Создайте файл `.env` с переменными (не загружайте в Git!)
- Убедитесь, что `client/index.html` ссылается на скомпилированный JS (или используйте простую структуру)
- В `package.json` добавьте скрипты:
  ```json
  "scripts": {
    "start": "node server/index.js",
    "server": "nodemon server/index.js"
  }
  ```

#### 6.2 Деплой на Render.com
1. Создайте репозиторий на GitHub, загрузите код.
2. Зарегистрируйтесь на [Render.com](https://render.com), нажмите **New +** → **Web Service**.
3. Подключите GitHub репозиторий.
4. Настройки:
   - **Build Command:** `npm install`
   - **Start Command:** `npm start`
   - **Environment Variables:** добавьте `MONGO_URI` (ссылка на MongoDB Atlas), `JWT_SECRET`, `PORT=10000`
5. Нажмите **Create Web Service**. Через 3-5 минут приложение будет доступно.

#### 6.3 Документация в GitHub (обязательно)
- **README.md** — этот документ (но адаптированный под вашу игру).
- **Issues:** создайте минимум 3 задачи (например, «Добавить анимацию удара», «Настроить WebSocket реконнект», «Сделать магазин скинов»).
- **Projects:** сделайте канбан‑доску с колонками `To Do` / `In Progress` / `Done`.
- **Wiki:** опишите управление, схему базы данных, API эндпоинты.
- **About репозитория:** заполните описание, укажите **website** (ссылка на Render), добавьте теги: `multiplayer`, `threejs`, `nodejs`, `game`.

## 🚀 Инструкция по деплою на Render.com

<details>
<summary><b>Подробный гайд (развернуть)</b></summary>

1. **MongoDB Atlas** — создайте бесплатный кластер, получите строку подключения.
2. **GitHub** — залейте код, убедитесь что в корне есть `package.json` и `server/index.js`.
3. **Render**:
   - Dashboard → New Web Service
   - Connect repository
   - Name: `your-game-multiplayer`
   - Environment: `Node`
   - Build Command: `npm install`
   - Start Command: `npm start`
   - Add Environment Variable:
     - `MONGO_URI` = `mongodb+srv://...`
     - `JWT_SECRET` = `случайная_строка`
     - `PORT` = `10000`
   - Нажать "Create Web Service"
4. После деплоя откроется лог. Если видите `Server running on port 10000`, переходите по адресу `https://your-game-multiplayer.onrender.com`.
5. **Проверьте мультиплеер** — откройте игру в двух разных браузерах или на двух устройствах, создайте комнату и убедитесь, что игроки видят друг друга.
</details>
